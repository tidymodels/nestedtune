## 1. The estimand

tidyclust 0.3.2 ships four metrics that `tune_cluster()` can tune on: `sse_within_total`, `sse_total`, `sse_ratio` and `silhouette_avg`. `sse_within()` and `silhouette()` return tables and are not metrics. A user can add one with `new_cluster_metric()`, whose signature is `function(object, new_data)`. Every metric is scored with the fitted workflow and a `new_data` frame, so the outer-fold quantity is defined for all four. The question is whether it is worth having.

Under the brief's procedure the outer fold scores `metrics(fit, new_data = assessment)`. For each metric that is:

- **`sse_within_total`.** Each assessment row is assigned to the nearest training centroid (`sse_within()`, the `new_data` branch) and its squared Euclidean distance to that centroid is summed. The outer average estimates the expected quantization error of the procedure's codebook on new rows, the loss Fu and Perry (2020) and the vector-quantization literature use. It is a property of the tune-and-fit procedure in IP3's sense. Two things reduce its worth. It is a sum, so it scales with the assessment set size, and `collect_metrics()` averages folds of unequal size on unequal scales. And in expectation it falls with k on held-out rows as well as on training rows: on one Gaussian with no clusters the held-out value went 792, 662, 572, 513, 468, 439, 398, 369, 357, 332 for k = 1 to 10, and on three separated Gaussians it kept falling past the true k (794 at k = 3, 544 at k = 10). The brief's concern is confirmed by the run: `select_best()` on `sse_within_total` chose k = 8, the top of the grid, on every outer fold of both data sets. The estimand under that rule is the quantization error of the largest k the grid allowed. It is well defined and IP4 can record it, but a user acts on the grid edge, not on the data. `select_by_one_std_err(num_clusters)` gave k = 6 on the same run; that is a complexity penalty with no stated justification, the tie-break `krstajic2014.md` records, not a rule the literature backs for k.

- **`sse_total`.** The sum of squared distances of the assessment rows to the training grand mean (the `n_members`-weighted mean of the centroids, which equals the training mean for every k). It is constant in k: 2171 on every grid row of the inner run. The outer average estimates `p * sigma^2 + mean_g ||mu_g - mu||^2`, a property of the data distribution and not of the tuning (measured 35.97 against a closed form of 36, see section 3). Selecting on it is degenerate: `select_best()` returns the first tied row, k = 1, with no warning.

- **`sse_ratio`.** `sse_within_total / sse_total` on the same rows. Scale-free, which fixes the first problem above, and monotone in k for the same reason as the numerator. `select_best()` picked k = 8 on every fold.

- **`silhouette_avg`.** The assessment rows are labelled by `predict()`, pairwise distances are computed within the assessment set, and the mean silhouette width (Rousseeuw 1987) is taken. It is not monotone: on the separated mixture the held-out value peaked at the true k (0.676 at k = 3, 0.50 at k = 4, 0.15 at k = 10), and `select_best()` chose k = 3 on every fold. The outer average estimates the expected mean silhouette of the procedure's assignment of new rows. It is a property of the procedure, it has a reading the literature supplies (Rousseeuw's bands: above 0.7 strong structure, 0.5 to 0.7 reasonable, 0.25 to 0.5 weak, below 0.25 none), and a user could report it. Three caveats. It is undefined at k = 1 (`NaN`), so the procedure can never select "no clusters": on one Gaussian it chose k = 2 on every fold and reported 0.18, which a reader has to know how to read. It costs O(n^2) distances per assessment set. And it describes how well training centroids partition new rows, not how well they recover any truth.

So the outer-fold average is well defined for all four, is a property of the procedure for all four, and is worth reporting for one. For the three sum-of-squares metrics, selection by the best inner mean picks the grid edge, so the thing the nested estimate describes is settled by the user's grid before any data is seen. That is the precise form of the README's objection, and it is a selection problem, not an estimand problem.

A note on IP3's obligation. For a supervised run the package can tell the user to report the nested estimate for the model `nested_final_fit()` returns. For a clustering run the parallel sentence is "report the expected out-of-sample silhouette of the procedure", and the fold-level `k` in `.selected` is at least as informative as the metric. `collect_selections()` and `agreement()` already exist and would carry the useful part of the result.

## 2. The mechanics

What exists:

- `tune_cluster()` returns a `tune_results` object (`new_tune_results()`), with `parameters`, `metrics` and `rset_info` attributes in tune's shape. `tune::collect_metrics()`, `show_best()`, `select_best()`, `select_by_one_std_err()` and `select_by_pct_loss()` all read it. Directions are honoured: `zero` on the SSE metrics selects the smallest mean, `maximize` on the silhouette selects the largest. `tune::finalize_workflow()` finalizes a cluster workflow; tune's `finalize_model()` accepts a `cluster_spec` and tidyclust 0.3.0 deprecated its own `finalize_*_tidyclust()` in favour of it.
- `fit()` on the finalized workflow fits on the analysis set. `predict()` assigns new rows per engine: nearest centroid for k-means (`flexclust::dist2()`), a per-linkage rule for `hier_clust()`, `mclust`'s `predict()` for `gm_clust()`, `dbscan::frNN()` over core points for `db_clust()` with an outlier cluster, and `meanShiftR::meanShift()` for `mean_shift()`.
- A `cluster_metric_set` is callable as `ms(fit, new_data = assessment)` and returns the `.metric`, `.estimator`, `.estimate` table tune expects. With a recipe or formula preprocessor the metric bakes `new_data` through the trained preprocessor (`extract_post_preprocessor()`), so the outer scoring is leak-free in IP1's sense if the fit saw only the analysis set.
- `tune_cluster()` takes a `tune::control_grid()`; tidyclust's `control_cluster()` exists but `tune_cluster.workflow()` condenses against `control_grid()`. A registry entry would read `package = "tidyclust"`, `control_class = "control_grid"`, `takes_grid = TRUE`, `selects = TRUE`.

What is missing: **`tune::last_fit()` does not accept a cluster workflow.** With a `cluster_metric_set` it stops in `check_metrics_arg()` with "The `metrics` argument should be the results of `yardstick::metric_set()`"; with `metrics = NULL` the mode switch in the same function stops with "Model value \"partition\" can't be used". `fit_resamples()` and `tune_grid()` stop at the same check. The refusal is in that one argument check: `last_fit_workflow()` builds a one-row `manual_rset()` and calls `resample_workflow()`, whose loop already supports cluster models. tune's `.make_static()` types a `cluster_metric_set` as `metric_type = "model"`, and `.loop_over_all_stages()` then fits the workflow on the analysis set and scores it with `static$metrics(current_wflow, new_data = static$data$pred$data)`, the assessment set. That is also how `tune_cluster()` scores its assessment sets: tidyclust 0.3.2's `tune_cluster_loop()` is a thin wrapper that calls `tune::.make_static()` and `tune::loop_call()`, so the per-resample fit and the `new_data` scoring are tune's code. There is no `.predictions` column for model metrics. So the outer step is one argument check away from working upstream. tidyclust's issue tracker holds nothing on `last_fit()` or `fit_resamples()`.

On nestedtune's side, the fold's outer step is `tune::last_fit()` at `R/nested-tune-grid.R:528`, so every fold would fail at "outer fit" today. `check_metrics()` (`R/checks.R:2310`) would pass a `cluster_metric_set`, since it inherits `metric_set`; `check_metrics_mode()` resolves the first metric through tune and would refuse before the loop. `compute_metrics()` and `check_score_metrics()` assume yardstick classes and saved predictions, which a cluster run has neither of. Without the upstream change, nestedtune would have to write its own outer fit-and-score (fit the finalized workflow on `analysis(split)`, call the metric set with `new_data = assessment(split)`), a second scoring path for one model class, which is the thing D-002 delegates.

## 3. The oracle

Three candidate oracle types, and what each pins:

1. **A simulated mixture with known within-cluster variance, closed form at fixed k.** With k equal to the true number of components and well separated means, each assessment row's expected squared distance to its estimated centroid is `p * sigma^2 * (1 + 1/n_c)`, `n_c` the rows per cluster in the analysis set, plus a misassignment term that is negligible at separation 6. For p = 4, sigma = 1, n = 300, 5 outer folds, that is 4.05 per assessment row. Twenty replicates of the by-hand nested run selecting on `silhouette_avg` gave a per-row `sse_within_total` of 4.058 (sd 0.165, se 0.037). `sse_total` has the closed form `p * sigma^2 + mean_g ||mu_g - mu||^2` = 36 for the means used; measured 35.97. This is a GP2-grade oracle for the nested number itself, not only for the selected k, under one condition: every outer fold selects the same k. That held on 100 of 100 folds at separation 6 and 98 of 100 at separation 3. A test can assert both, because `.selected` records k per fold (IP4). Under SSE selection the same oracle pins the value at the grid's top k, which verifies code and nothing about meaning.

2. **A null-data invariant, after `varma2006.md`.** On one Gaussian, 2-means splits along one axis with centers at plus and minus `sigma * sqrt(2/pi)` in the limit, so the held-out `sse_ratio` at k = 2 tends to `1 - 2/(pi * p)`, which is 0.841 at p = 4; one data set gave 0.836. Since silhouette selection chose k = 2 on every null fold, this is a second closed form for a nested SSE number, again at a fixed selected k. For the silhouette itself there is no closed form on null or mixture data; the only invariant is that it rises with separation and sits in Rousseeuw's "none" band on null data (0.10 to 0.18 observed), which is a sanity check and not an oracle.

3. **A stability reference.** Prediction strength (Tibshirani and Walther 2005), the stability risk of Lange et al. (2004), Wang's (2010) instability, and the perturbation methods of Ben-Hur, Elisseeff and Guyon (2002) all give a known answer for the selected k under separation (prediction strength near 1 for k at or below the true k, falling after). None gives a value for a tidyclust metric. They would be oracles for `.selected`, not for `collect_metrics()`.

So two independent oracle types exist for `sse_within_total`, `sse_total` and `sse_ratio` at a fixed selected k, and none for `silhouette_avg`. The metric with an oracle has degenerate selection; the metric with meaningful selection has no oracle. That is the real reason the row cannot ship a number under GP2 today, and it is sharper than "no oracle exists".

## 4. Fit with the principles

**Is cross-validated choice of k contested?** Yes, and the literature has a clear shape. Everyone agrees that cross-validating the quantization loss does not choose k, because the held-out loss keeps falling (Tibshirani and Walther 2005 open with this; Hastie, Tibshirani and Friedman, *Elements*, section 14.3.11; the tidyclust article says the same in its own words). The proposals replace the loss with something else: a held-out prediction criterion (prediction strength, which Tibshirani and Walther treat as a classification problem and read against a 0.8 to 0.9 threshold), a stability risk (Lange et al. 2004, Neural Computation 16:1299-1323; Wang 2010, Biometrika 97:893-904, with a consistency proof under proper splitting; Ben-Hur et al. 2002, PSB 7:6-17), or a block hold-out that makes the problem supervised (Fu and Perry 2020, JCGS 29:162-173, doi 10.1080/10618600.2019.1647846). Against stability, Ben-David, von Luxburg and Pál (COLT 2006, "A sober look at clustering stability") and von Luxburg (2010, *Foundations and Trends in ML* 2:235-274) show that for k-means stability tracks whether the objective has a unique minimizer, so it can select a wrong k on symmetric data and is reliable mainly where clusters are well separated. Hennig (2015, Pattern Recognition Letters 64:53-62) argues there is no single true k independent of the aim. The side the literature favours for *choosing k* is stability or prediction strength over the training objective, with known failure modes. No source on the shelf or found here treats the nested average of an internal validity index as the quantity to report.

**GP5.** GP5 is about inference, and the nested number here is a point estimate of a procedure's out-of-sample index, so the conflict is indirect. It becomes direct in one place: shipping SSE-selected nested estimates would present as a tuning procedure something the literature says is not a procedure for choosing k. That is picking a side, the losing one. Silhouette-selected estimates are defensible but rest on a criterion the literature treats as one option among several.

**IP3.** Holds formally for every metric. Its obligation, say what to report instead, is where it bites: for an SSE-selected run the honest sentence is "the fit at the largest k you allowed", which no documentation should instruct a user to report.

**IP4.** Satisfied by the existing results object: `.selected` would show k per fold, and the grid actually evaluated is recorded.

**GP3** is the principle most at risk. `sse_total` is constant in k and selects k = 1 silently; `select_best()` on the two other SSE metrics selects the grid edge silently. A milestone would have to refuse or redirect those, which means nestedtune judging a tidyclust metric's suitability for selection, a judgment that belongs upstream.

## 5. The disposition

**Keep parked (b).** The reasons, in order of weight: the outer step cannot be delegated today, because `tune::last_fit()` refuses a cluster workflow, and the alternative is a nestedtune-owned scoring path against D-002; the only metric on which selection is meaningful has no oracle, so GP2 cannot be met for the case worth shipping; and the row came from a list of tuners, not from a use. Nothing in IP1 to IP4 forbids the feature, the estimand is defined, and the oracle gap is narrower than the row says, so this is not a rejection on principle.

**Promotion condition, as a class of evidence:** both of the following.

1. The outer fold can be delegated: tune accepts a cluster workflow and a `cluster_metric_set` in `last_fit()` (the loop beneath it already does), or tidyclust ships a `last_fit()` counterpart that scores with `new_data`. Evidence is a released version in which `tune::last_fit(finalized_cluster_workflow, split, metrics = cluster_metric_set(...))` returns metrics.
2. A second oracle type exists for a metric on which selection is not degenerate: a published closed form or reference value for an out-of-sample silhouette under a known mixture, or a metric tidyclust ships whose population value is known under separation (a prediction-strength metric, whose limit is 1 at the true k, would do). Evidence is the source or the released metric, not a request count.

**If it is promoted anyway, the smallest defensible scope (a):** `nested_tune_cluster()` as one registry entry (`tune_cluster`, package tidyclust, `control_grid`, `takes_grid`, `selects`), `metrics` restricted to a `cluster_metric_set`, `k_means()` on the `stats` engine in tests, selection refused on `sse_total` and documented as picking the grid edge on `sse_within_total` and `sse_ratio` under `"best"`, the first metric required to be `silhouette_avg` or a user metric with direction `maximize`. Oracles: the fixed-k mixture closed form (section 3, type 1) and the null k = 2 ratio (type 2), both asserting the selected k alongside the value. Dependency: tidyclust in Suggests, which pulls `flexclust`, `philentropy` and `mclust`; that is the D-entry the row names. Plus the upstream change to tune, without which the scope includes an own outer fit-and-score path and should not be approved.

**Drop (c)** is not recommended. If the maintainer prefers it, the sentence a decision record could carry is: "nestedtune ships a nested estimate only where the inner selection rule is one the literature treats as a procedure for the parameter it selects; for the number of clusters, held-out sum-of-squares selection is not one, and the metric on which selection is meaningful has no oracle." It would reopen on the same evidence as the promotion condition above.

## 6. The README row

The sentence "nothing yet settles what a nested estimate of a clustering metric means" is not accurate. The estimate is defined for every metric tidyclust ships: the expected value of that metric when the procedure's fitted partition is applied to new rows. What blocks the row is mechanical and selectional, not semantic. Replacement, two sentences:

> `tune::last_fit()` does not accept a clustering workflow, so no nestedtune function can score the outer fold. Selecting on a sum-of-squares metric also picks the largest number of clusters in the grid, so the estimate would describe the grid and not the data.

The ROADMAP row's "no oracle exists" should change in the same way: a closed-form oracle exists for the SSE metrics at a fixed selected k, and none for the silhouette.

## Beyond the brief

1. **tidyclust bug, `hier_clust()` only.** `extract_fit_summary.hclust()` sums unsquared Euclidean distances for `sse_total` (and for the within totals, though `sse_within()` recomputes those from the stored training data and squares them). So `sse_total()` and `sse_ratio()` on a fitted `hier_clust()` with no `new_data` return different quantities from the `new_data` path: on one 200 by 3 fixture, 328.6 against 627.9 for the total and a ratio of 1.16 against 0.61. `tune_cluster()` always passes `new_data`, so inner results are unaffected, but a user comparing an in-sample `sse_ratio()` to a nested one for `hier_clust()` compares different things. Worth an upstream issue; it is not nestedtune's to fix.
2. **A prediction-strength metric is expressible in tidyclust's extension API.** `new_cluster_metric()` takes `function(object, new_data)`; the function can cluster `new_data` at the fitted model's k, compare co-membership with `predict(object, new_data)`, and return Tibshirani and Walther's statistic. Its nested average has a reading the literature supplies and a known limit under separation, so it is the metric that would satisfy condition 2 above. It belongs in tidyclust, not here.
3. **`sse_within_total` is a sum.** tune's `collect_metrics()` averages per-resample values, so folds of unequal size are averaged on unequal scales. `sse_ratio` or a per-row mean is the quantity to put in a table; a milestone should say so or refuse the sum as the first metric.
4. **Unverified.** Whether `nested_resamples()` and the entry checks assume an outcome column anywhere a `partition`-mode workflow would trip them. `tune::outcome_names.workflow()` returns `NULL` for a `cluster_spec`, so tune is prepared; nestedtune's checks were not traced for this.
5. The brief's constraints are accepted as written. The one place the review leans on them is scope (a): without the tune change, the smallest scope violates D-002, so the constraint and the recommendation agree.

## Recommendations

- **R1 (apply).** Keep the row parked and rewrite its condition to the two-part evidence class in section 5: a delegable outer fit, and a second oracle type for a metric on which selection is not degenerate. Replace "no oracle exists" with "a closed-form oracle exists for the SSE metrics at a fixed selected k, none for the silhouette".
- **R2 (apply).** Replace the README sentence with the two sentences in section 6.
- **R3 (consider).** Ask tune, as the in-organization ask DESIGN.md already describes, to accept a `cluster_metric_set` and the `partition` mode in `check_metrics_arg()` so that `last_fit()` and `fit_resamples()` reach the loop that already scores cluster models. It is the whole mechanical blocker and costs tune one branch.
- **R4 (consider).** File the `hier_clust()` `sse_total` inconsistency (Beyond the brief 1) with tidyclust.
- **R5 (reject).** Promoting now with a nestedtune-owned outer fit-and-score for cluster workflows. Reason: a second scoring path for one model class against D-002, with no oracle for the one metric worth selecting on.
- **R6 (reject).** Dropping the row as rejected on principle. Reason: no inviolable principle forbids it, the estimand is defined for every metric, and both blockers are evidence that can arrive.
